TL;DR

  • Language models need a tokenizer to convert raw text (bytes) into integer sequences — the choice of tokenizer profoundly affects model efficiency.
  • There's a fundamental trade-off: vocabulary size (smaller = less sparse) vs compression ratio (higher = shorter sequences for Transformer).
  • BPE (Byte Pair Encoding) is the dominant tokenization method — it's data-driven, starts from bytes, and iteratively merges the most frequent adjacent pair.
  • Course philosophy: understanding via building. accuracy = efficiency × resources. Algorithms that scale are what matter.

Key Concepts

Tokenizer — Converts between raw strings and integer sequences (tokens). Must implement encode(str→list[int]) and decode(list[int]→str).
Compression Ratio — bytes / tokens. Higher is better: means shorter sequences for the Transformer. BPE achieves ~4x compression on English text.
BPE Training — Start with bytes (vocab=256). Repeat: count adjacent pairs → merge most frequent → add merged token to vocab. Each merge increases compression.
BPE Encoding — Given a string, convert to bytes, then apply learned merge rules in training order. Greedy left-to-right, rank-based resolution for overlaps.
Pre-tokenization — Split text on word boundaries (regex) before BPE to prevent cross-word merges. GPT-2 uses a regex that isolates words, numbers, punctuation.
Vocabulary Size — GPT-2: 50,257 tokens. GPT-4/5 (o200k): 200,019 tokens. Larger vocab = higher compression but sparser embeddings.
The Bitter Lesson — Not "scale is all that matters" but "algorithms that scale are what matter." Efficiency is more important at larger scales.
Three Types of Knowledge — Mechanics (how things work), Mindset (squeeze hardware), Intuitions (which decisions yield good accuracy). CS336 teaches the first two.

The Disconnection Problem

Researchers are becoming increasingly disconnected from underlying technology:

  • 2018: Researchers downloaded models (e.g., BERT) and fine-tuned them

Part 4: Tokenization

Inspired by Andrej Karpathy's tokenization video ↗. Play with tokenization interactively: tiktokenizer ↗

The Problem

A language model operates on sequences of integers (tokens), but raw input is a Unicode string (bytes). We need encode(str → list[int]) and decode(list[int] → str) that round-trip correctly.

Approach 1: Character Tokenizer

Map each Unicode character to its code point via ord().

class CharacterTokenizer(Tokenizer):
    def encode(self, string):
        return list(map(ord, string))  # ord("a")=97, ord("🌍")=127757
    def decode(self, indices):
        return "".join(map(chr, indices))
  • Vocab size: ~150K Unicode characters — huge and sparse
  • Compression: ~1 byte/token — poor
  • Worst of both worlds: large vocabulary AND low compression

Approach 2: Byte Tokenizer

Encode string as UTF-8 bytes. Each byte is a token (0-255).

class ByteTokenizer(Tokenizer):
    def encode(self, string):
        return list(map(int, string.encode("utf-8")))
    def decode(self, indices):
        return bytes(indices).decode("utf-8")
  • Vocab size: 256 — nice and small
  • Compression: exactly 1.0 — terrible (sequences are too long for Transformer's quadratic attention)
  • Multi-byte characters: "a" = 1 byte, "🌍" = 4 bytes, "你" = 3 bytes

Approach 3: Word Tokenizer

Split on whitespace/punctuation using regex like \w+|.

  • Compression: good (each token is a whole word)
  • Vocab size: unbounded — depends on data
  • Problems: rare words waste vocab slots, OOV (unseen words → UNK token), no fixed vocab size

Approach 4: Byte Pair Encoding (BPE) ★

Originally a data compression algorithm (Gage, 1994). Adapted to NLP by Sennrich et al. (2016), then used by GPT-2.

Core idea: train the tokenizer on data to build a vocabulary tailored to the corpus. Common byte sequences → single tokens. Rare sequences → many tokens.

BPE Training Algorithm

def train_bpe(string, num_merges):
    indices = list(string.encode("utf-8"))  # Start with raw bytes
    merges = {}
    vocab = {x: bytes([x]) for x in range(256)}  # Initial vocab: 256 bytes

    for i in range(num_merges):
        counts = count_adjacent_pairs(indices)  # Step 1: count pairs
        pair = max(counts, key=counts.get)       # Step 2: find most frequent
        new_index = 256 + i                      # Step 3: assign new token ID
        merges[pair] = new_index
        vocab[new_index] = vocab[pair[0]] + vocab[pair[1]]
        indices = merge(indices, pair, new_index) # Step 4: replace all occurrences

    return BPETokenizerParams(vocab=vocab, merges=merges)

BPE Training Example

Training on "the cat in the hat" with 3 merges:

Each merge step: vocab size +1, compression ratio increases.

BPE Encoding (Using the Trained Tokenizer)

class BPETokenizer(Tokenizer):
    def encode(self, string):
        indices = list(string.encode("utf-8"))
        for pair, new_index in self.params.merges.items():
            indices = merge(indices, pair, new_index)
        return indices

    def decode(self, indices):
        return b"".join(self.params.vocab[i] for i in indices).decode("utf-8")

Note: this naive implementation loops over all merges for every string. Assignment 1 requires an efficient version.

The merge() Helper

def merge(indices, pair, new_index):
    new_indices = []
    i = 0
    while i < len(indices):
        if i+1 < len(indices) and indices[i]==pair[0] and indices[i+1]==pair[1]:
            new_indices.append(new_index)
            i += 2  # Skip both elements of the pair
        else:
            new_indices.append(indices[i])
            i += 1
    return new_indices

Key Observations from Tokenizer Playground

  • A word and its preceding space are often the same token: " world" ≠ "world"
  • Same word at start vs middle of sentence → different tokens
  • Numbers get split every few digits
  • GPT-5 (o200k) vocab size: 200,019 tokens

Whatever solution needs: (1) model operates on chunks/abstractions of the sequence, (2) chunks should be variable-length (allocate more capacity to interesting parts).
