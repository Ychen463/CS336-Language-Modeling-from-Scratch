Key Concepts

GPU Kernels & Operator Fusion
Kernel Fusion — combine multiple elementwise operations into a single GPU kernel to reduce memory bandwidth overhead.
核融合——将多个逐元素操作合并为一个 GPU 核，减少显存带宽开销。
RMSNorm — Root Mean Square Layer Normalization: $\text{RMSNorm}(x) = \frac{x}{\sqrt{\frac{1}{d}\sum x_i^2 + \epsilon}} \cdot \gamma$. Simpler than LayerNorm (no mean subtraction).
均方根归一化：比 LayerNorm 更简单（无需减均值）。
Triton — Python-based GPU programming language from OpenAI. Write kernels in Python that compile to optimized GPU code.
OpenAI 的 Python GPU 编程语言，用 Python 写核函数并编译为优化的 GPU 代码。
Distributed Training
Data Parallel (DDP) — each GPU has full model copy, processes different data, synchronizes gradients via all-reduce.
数据并行——每个 GPU 拥有完整模型副本，处理不同数据，通过 all-reduce 同步梯度。
All-Reduce — collective communication: sum gradients across all GPUs and broadcast the result back. Ring all-reduce is bandwidth-optimal.
集合通信：将所有 GPU 的梯度求和并广播回来。Ring all-reduce 是带宽最优的。
ZeRO-1 (Optimizer Sharding) — each GPU stores only 1/N of optimizer states (e.g., Adam's m and v). Reduces memory by ~4× for Adam.
每个 GPU 只存 1/N 的优化器状态（如 Adam 的 m 和 v），内存减少约 4 倍。
Scaling Laws
Scaling Recipe — a mapping from FLOPs budget → hyperparameters (model size, tokens, LR, etc.). Run small-scale experiments, fit power laws, extrapolate to target scale.
缩放配方——从 FLOPs 预算到超参数的映射。在小规模上实验，拟合幂律，外推到目标规模。
µP (Hyperparameter Transfer) — parameterize the model so optimal hyperparameters (e.g., LR) stay stable across widths. Tune once at small scale, reuse at large scale [Yang+ 2022].
最大更新参数化——让最优超参数在不同宽度间稳定。小规模调一次，大规模直接用。
Compute-Optimal Scaling — given $C = 6ND$ FLOPs, optimal ratio is roughly $D \approx 20N$ (Chinchilla). Caveat: doesn't account for inference costs.
计算最优缩放——给定 $C = 6ND$，最优比例约为 $D \approx 20N$。注意：未考虑推理成本。

Fused RMSNorm Kernel

Why Kernel Fusion?

Naive RMSNorm requires multiple kernel launches: compute sum of squares, compute RMS, normalize, scale. Each launch reads/writes to global memory (HBM).（朴素 RMSNorm 需要多次核启动，每次都读写全局显存。）

A fused kernel does everything in one pass: reads input once, computes in registers/shared memory, writes output once. This is memory-bound, so reducing memory traffic is the key optimization.（融合核一次完成所有操作：读入一次，在寄存器/共享内存中计算，写出一次。这是内存瓶颈型操作。）

Triton Implementation

Triton operates on blocks of data (not individual threads like CUDA). You specify block sizes, and Triton handles thread management, memory coalescing, and vectorization.

Triton 以数据块为单位操作（不像 CUDA 那样操作单个线程）。你指定块大小，Triton 负责线程管理、内存合并和向量化。

Key operations: tl.load, tl.store, tl.sum, tl.sqrt. The forward kernel computes the normalized output; the backward kernel computes gradients for both input and the scale parameter $\gamma$.

Distributed Data Parallel (DDP)

How DDP Works

  1. Each GPU gets a full copy of the model（每个 GPU 获得完整模型副本）
  2. Each GPU processes a different mini-batch (data parallelism)（每个 GPU 处理不同的 mini-batch）
  3. After backward pass, all-reduce gradients across GPUs（反向传播后，跨 GPU all-reduce 梯度）
  4. Each GPU applies the same optimizer step → models stay synchronized（每个 GPU 执行相同的优化器步骤 → 模型保持同步）

Overlapping Communication & Computation

Naive DDP: compute all gradients, then all-reduce. Better: overlap gradient communication with backward computation using bucketed all-reduce — start communicating early layers' gradients while still computing later layers'.

朴素 DDP：先计算所有梯度，再 all-reduce。更好的方式：使用分桶 all-reduce 将梯度通信与反向计算重叠——在计算后面层的梯度时就开始通信前面层的梯度。

Optimizer State Sharding (ZeRO-1)

Adam stores 2 extra states per parameter (first moment $m$ and second moment $v$), tripling memory compared to SGD. With $N$ GPUs:

  • Each GPU stores optimizer states for only $1/N$ of the parameters（每个 GPU 只存 1/N 参数的优化器状态）
  • After all-reduce of gradients, each GPU updates only its shard（梯度 all-reduce 后，每个 GPU 只更新自己的分片）
  • Updated parameters are broadcast back (all-gather)（更新后的参数通过 all-gather 广播回去）
ZeRO-1 trades a small amount of extra communication (all-gather) for a large memory saving (~4× for Adam with fp32 states).
ZeRO-1 用少量额外通信（all-gather）换取大量内存节省（Adam fp32 状态约 4 倍）。

Scaling Laws Preview

The Core Problem

Setting: if you had $10^{25}$ FLOPs of compute, what hyperparameters would you use to train a good model? Too expensive to do hyperparameter tuning at full scale!（假设你有 $10^{25}$ FLOPs 的算力，你会用什么超参数？在全规模上调参太贵了！）

Key conceptual shift: instead of a single scale, think of a scaling recipe (FLOPs → hyperparameters).（关键思维转变：不要想单个规模，而是想缩放配方：FLOPs → 超参数。）

Building a Scaling Recipe

  1. Run experiments to compute the loss at various smaller scales (e.g., up to $10^{24}$ FLOPs)（在较小规模上运行实验计算损失）
  2. Fit a scaling law to predict the loss at the target scale (e.g., $10^{25}$ FLOPs)（拟合缩放定律预测目标规模的损失）

Now you can:

  • Optimize the scaling recipe targeting a larger scale using smaller scale experiments（用小规模实验优化针对大规模的缩放配方）
  • Predict the loss at the target scale before actually running the experiment!（在实际运行实验前预测目标规模的损失！）
Scaling laws don't happen automatically — they require careful construction of a scaling recipe.
缩放定律不会自动出现——需要精心构建缩放配方。
Predictability is at least as important as optimality!
可预测性至少和最优性一样重要！

Hyperparameter Transfer (µP)

A scaling recipe only works if hyperparameters transfer across scales — i.e., the optimal learning rate found at small scale is also (approximately) optimal at large scale. This doesn't happen by default with standard parameterization.（缩放配方只有在超参数能跨规模迁移时才有效——即小规模找到的最优学习率在大规模也近似最优。标准参数化下这不会自动成立。）

µP (Maximal Update Parameterization) [Yang+ 2022] solves this by carefully scaling initialization, learning rates, and multipliers per layer so that the magnitude of activations and updates stays consistent as model width changes. Key ideas:

µP（最大更新参数化）通过精心缩放每层的初始化、学习率和乘子，使激活和更新的幅度在模型宽度变化时保持一致。

  • Standard parameterization (SP): optimal LR changes with width — can't transfer（标准参数化：最优 LR 随宽度变化——无法迁移）
  • µP: optimal LR is stable across widths — tune once at small scale, use at large scale（µP：最优 LR 在不同宽度间稳定——小规模调一次，大规模直接用）
Without hyperparameter transfer, scaling laws are useless — you'd need to re-tune at every scale, defeating the purpose.
没有超参数迁移，缩放定律就没用——你需要在每个规模上重新调参，违背了初衷。

Compute-Optimal Scaling (Chinchilla)

Question: given a FLOPs budget ($C = 6ND$), use a bigger model ($N$) or train on more tokens ($D$)?

问题：给定 FLOPs 预算（$C = 6ND$），应该用更大的模型（$N$）还是训练更多 token（$D$）？

Classic compute-optimal scaling laws [Kaplan+ 2020] [Hoffmann+ 2022]:

  1. ISOFLOP curves: for multiple small FLOPs budgets, find optimal $N$（等 FLOPs 曲线：对多个较小 FLOPs 预算找最优 $N$）
  2. Then fit a scaling law to extrapolate to large FLOPs budgets（然后拟合缩放定律外推到更大 FLOPs 预算）

Chinchilla ISOFLOP analysis [Hoffmann+ 2022]: (Left) Loss vs parameters for fixed FLOPs — each curve's minimum gives compute-optimal model size. (Middle/Right) Optimal $N$ and $D$ scale as power laws with FLOPs.

TL;DR: $D = 20N$ is roughly optimal. E.g., 70B parameter model should be trained on ~1.4T tokens.（简言之：$D = 20N$ 大致最优。如 70B 参数模型应训练约 1.4T tokens。）

Caveat: this doesn't take into account inference costs — in practice you may want a smaller model trained on more tokens.（注意：没考虑推理成本——实际中可能想用更小模型训练更多 token。）
